# 设计取舍（ADR）

按编号记录关键决定、理由、以及被否决的替代方案。改代码前先读这一页。

---

## ADR-001 网关是控制面，不是更聪明的 Agent

**决定**：网关持有调度循环、路由策略、能力凭据与账本；Agent 降级为"被调用的能力"。

**理由**：之前"一个 Agent 拖 N 个 MCP"的问题不是 Agent 不够聪明，而是每份知识都长在
会话里——换一个 Agent 就重来一遍，MCP 用得少也没人知道为什么。把控制权收回到一个常驻
进程，知识才可能变成资产。

**否决**：让 Agent 自己调一个"MCP 路由器"工具。这样路由仍然发生在模型的选择里，
不可审计、不可 pin、不可 A/B。

**代价**：网关成为单点与信任边界。用"能力版本钉死 + 每实例作用域 + 决策链"来兜。

---

## ADR-002 环境（env）是封装单位，不是沙箱

**决定**：env 同时承担依赖、凭据、版本、隔离、失败五种边界，按**业务域**切
（crawler / chain-watch / doc-qa），不按技术切（browser / http / db）。

**理由**：按技术切会让每个任务都要拉五六个环境，编排成本先压垮人；按业务域切，
一个 env 内部的组合是稳定的，性能画像才有统计意义。

**否决**：一个能力一个 env。粒度太碎，产物契约会爆炸。

---

## ADR-003 异构适配器下沉到环境里

**决定**：网关只认 `adapter + models + recipe`；MCP 客户端、Agent 框架、CLI 的差异
全部关在 env 内部。

**理由**：这是"异构不变成 N×M 适配矩阵"的唯一走法。新增一个框架 = 新增一个 adapter
实现 + 一个 env 声明，网关零改动。

**否决**：网关内置各家 Agent 的客户端。每接一家都要改控制面，控制面会变成垃圾场。

---

## ADR-004 双层路由，探索本地化

**决定**：第一层网关选领域，第二层 env 选模型。

**理由**：全局 `(任务 × env × agent × model)` 的样本永远不够；域内任务同质，
`(任务类型 × agent/model)` 学得动。探索也可以本地化，每个域自己跑 A/B。

---

## ADR-005 Thompson sampling 而不是 epsilon-greedy

**决定**：Beta-Bernoulli 后验采样，先验用 `prior` 当量表示；`epsilon` 与 `static` 保留为
备选与基线。

**理由**：epsilon-greedy 的探索是"无差别随机"，会拿差候选浪费配额；Thompson 的探索
集中在"还不确定"的候选上，正好治"第一个还行的组合被锁死"这个病。

**否决**：`mabwiser` 等 bandit 库。停更、依赖 numpy、context-free 场景本就要自己做
特征化，30 行自实现更可控（`random.betavariate`）。

---

## ADR-006 env 之间禁止直连，只走产物库

**决定**：产物内容寻址落盘，下游只拿到自己 `consumes` 声明的那些。

**理由**：直连会退化成不可追溯的点对点网络——不能重放、不能计费、出事定位不到
"谁吐了什么"。禁止直连还顺带把"数据长什么样"变成显式契约。

**代价**：多一次读写；大产物（视频等）需要对象存储，见 ARCHITECTURE 的规模假设。

---

## ADR-007 起点必须能独立启动

**决定**：`_pick_head` 跳过依赖上游产物的 env；调整起点时写进决策理由。

**理由**：路由的最高分候选可能是个只能接力的 env，直接开端会注定失败，而且失败原因
会伪装成"环境坏了"。

**教训**：这条是踩出来的——第一版把 `analyst` 排成起点，任务一开局就挂。

---

## ADR-008 先账本，后算法

**决定**：第一期只做决策链 + 聚合 + 人工验收标签；路由算法基于这些数据。

**理由**：没有样本和标签的打分是"我觉得"。而且决策链本身就是产品——路由再聪明，
解释不了就是黑盒，最后所有人都会手动指定，系统退化成启动器。

**否决**：先接一个大模型做路由。多一跳延迟、多一个失败面，且不可归因。

---

## ADR-009 人工标签压过自动判定

**决定**：`perf()` 的成败 = 运行成功 **且** 最新一条人工标签不是差评。

**理由**：自动判定只看运行状态。跑通但结果不能用，才是最常见的失败。
标签必须取最新一条，否则"人改主意"会被旧标签污染，也会导致 run 重复计数。

---

## ADR-010 失败策略逐节点声明

**决定**：`abort / degrade / retry-alt` 写在 env 上。

**理由**：并行分叉里，"链上查询挂了"不该让"采集结果"一起作废；反过来，
"采集挂了"对汇总是致命的。一刀切两种都会错。

**现状**：`retry-alt` 只降级并记事件，**没有真正换候选重跑**——见 README 已知限制。

---

## ADR-011 MCP 连接由一个常驻 host task 持有

**决定**：每次连接开一个 task 进 `AsyncExitStack`，业务侧只拿 session 调用。

**理由**：MCP stdio 客户端上下文必须在同一 task 里进出；否则调用方一取消，
子进程就泄漏。顺带让"共享能力单例"变得自然。

**代价**：每个共享 MCP 一个常驻子进程。用 `shared: false` 可以换回按 env 隔离。

---

## ADR-012 版本用 PEP 440 说明符，解析结果落账

**决定**：env 写 `>=0.1,<0.2`，解析到确切版本后写进 `runs.meta.resolved`。

**理由**：共享能力一定会升级，共享层升级不能悄悄击穿所有域。同时"半年后回看这次运行
用的是哪个版本"必须答得出来。

**否决**：直接写死版本号。升级时要改所有 env。

---

## ADR-013 演示数据必须自我标注

**决定**：`sdk-chain` 的余额是确定性伪数据，返回体里带 `source: demo-deterministic` 与
`note: 演示数据，非真实链上查询`。

**理由**：演示桩被当成真实能力是这类项目最常见的翻车方式。宁可丑，不可假。

---

## ADR-014 能力白名单：默认暴露最少

**决定**：`CapabilityVersion.tools` 是白名单。BCA 暴露 125 个工具，`mcp-bca` 只放行 7 个。

**理由**：工具描述会占上下文。把 125 条描述塞给模型，挤掉的是真正要用的那几个；
而且大部分工具（签名、写链、IPFS 上传）在自动链路里根本不该被随手调用。

**代价**：新用法要改白名单。可以接受——白名单变更是一次显式的授权动作，
这正是我们想要的。

**否决**：全量暴露 + 靠描述筛选。模型对"哪些不该调"没有可靠判断。

---

## ADR-015 能力路径用 `${VAR:default}` 展开，不写死

**决定**：`command / args / cwd / url / env` 支持 `${CAPGATE_BCA_HOME:C:/...}` 语法，
在 `Pool.resolve` 时展开。

**理由**：能力声明要能在不同机器上跑，又不能强迫使用者先配一堆环境变量。
默认值让"本机能跑"和"换机器只改一处"同时成立。

**代价**：默认值里仍有绝对路径。这是本地网关的合理妥协——真正的分发形态
应该由 `capgate init` 生成本机配置，见 issue #012。

---

## 待定

- **产物 TTL 与引用计数**：现在只增不删。
- **流式产物**：目前 env 之间只能整块交接；低延迟链路需要受控的例外通道。
- **多进程**：账本与产物库都假设单写者。
- **`llm_fallback`**：钩子已留（`Router.judge`），缺一个实现与评估。
